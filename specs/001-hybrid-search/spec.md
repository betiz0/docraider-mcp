# Feature Specification: Hybrid Search (Keyword + Semantic)

**Feature Branch**: `001-hybrid-search`

**Created**: 2026-06-13

**Status**: Implemented — validation passed 2026-08-19

**Input**: User description: "既存の全文検索（キーワード一致）に加えて、意味的に近い内容を見つけられるセマンティック検索を導入し、両者を組み合わせたハイブリッド検索を MCP ツールとして提供する。デフォルトはハイブリッド。新規クロール分は自動で意味検索対象、既存分はバックフィル。埋め込み未完了・失敗でもキーワード検索は従来どおり動作（段階的劣化）。結果にヒット方式とスコアを含める。監査レポートの Critical/High のうち検索品質・データ整合性に関わるものの修正を含む。日本語と英語が混在しても両言語のクエリで機能する。リランキングと検索 UI はスコープ外。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 言い換え・概念一致のクエリで取りこぼさない意味検索 (Priority: P1)

コーディングエージェントが自然文や、ドキュメント中の用語と完全には一致しない語でクエリを投げても、概念的に近い内容のドキュメントが返る。例として「認証」というクエリで、本文が "authentication" としか書かれていないドキュメントがヒットする。

**Why this priority**: 本機能の中核価値であり、現状の字面一致では取りこぼすクエリを救済する。これ単独でも検索品質が向上し、MVP として成立する。

**Independent Test**: 既知の「概念は同じだが用語が異なる」クエリ集合を用意し、意味検索モードで該当ドキュメントが上位に返ることを、キーワード検索のみの結果と比較して検証できる。

**Acceptance Scenarios**:

1. **Given** "authentication" のみを含む英語ドキュメントがインデックスされている, **When** クエリ「認証」で意味検索またはハイブリッド検索を実行する, **Then** そのドキュメントが結果に含まれる。
2. **Given** ある概念を異なる言い換えで説明したドキュメントがある, **When** その概念をユーザ独自の言い回しで問い合わせる, **Then** 字面が一致しなくても該当ドキュメントが返る。
3. **Given** クエリに完全一致するキーワードを含むドキュメントと、意味的に近いだけのドキュメントが両方ある, **When** ハイブリッド検索を実行する, **Then** 両者が統合ランキングに含まれ、関連度の高い順に並ぶ。

---

### User Story 2 - 検索方式を選べるハイブリッド検索ツール (Priority: P1)

呼び出し側が、キーワード検索・意味検索・ハイブリッド（両者の統合ランキング）の中から方式を選択でき、指定しなければハイブリッドが使われる。各結果には「どの方式でヒットしたか」と「スコア」が付与され、呼び出し側が結果の性質を判断できる。

**Why this priority**: 方式選択と結果メタデータは、エージェントが結果を信頼・取捨選択するための必須インターフェース。User Story 1 の価値を実利用可能な形で届ける。

**Independent Test**: 同一クエリを 3 方式で実行し、(a) デフォルトがハイブリッドであること、(b) 各結果に方式ラベルとスコアが含まれること、(c) 方式によって結果集合が変わることを検証できる。

**Acceptance Scenarios**:

1. **Given** 検索対象データが存在する, **When** 方式を指定せずに検索する, **Then** ハイブリッド方式で実行される。
2. **Given** 検索対象データが存在する, **When** 方式に「キーワード」「意味」「ハイブリッド」のいずれかを指定する, **Then** 指定方式で実行され、結果にその方式ラベルが反映される。
3. **Given** 検索結果が返る, **When** 結果を受け取る, **Then** 各結果項目にヒット方式（キーワード／意味／両方）と数値スコアが含まれる。
4. **Given** 不正な方式名が指定された, **When** 検索する, **Then** 明確なエラーが返り、無言でデフォルトに切り替わらない。

---

### User Story 3 - 既存ドキュメントのバックフィルと新規分の自動対象化 (Priority: P2)

新しくクロールされたドキュメントは自動的に意味検索の対象になる。既存のクロール済みドキュメントは、後から意味検索の対象に変換（バックフィル）する手段が提供され、進捗と完了状況が分かる。

**Why this priority**: 意味検索の網羅性を担保する運用機能。User Story 1/2 が動く前提として重要だが、初期は一部データだけでも価値が出るため P2。

**Independent Test**: 既存ドキュメントがある状態でバックフィルを実行し、対象件数・完了件数・失敗件数が報告され、完了後に意味検索でそれらがヒットすることを検証できる。新規クロール後、追加操作なしに意味検索対象になることも検証できる。

**Acceptance Scenarios**:

1. **Given** 意味検索化されていない既存ドキュメントがある, **When** バックフィル MCP ツールを呼び出す, **Then** 即座に受付応答（処理開始確認・対象件数見込み）が返り、バックグラウンドで処理が進む。進捗確認ツールで対象・完了・失敗件数を取得できる。
2. **Given** 新しいドキュメントをクロールする, **When** クロールが完了する, **Then** 追加操作なしにそのドキュメントが意味検索対象になる。
3. **Given** バックフィルが途中で中断・再実行される, **When** 再度バックフィルを実行する, **Then** 既に処理済みのものは二重処理されず、未処理分のみが対象になる。

---

### User Story 4 - 意味検索が未準備でも止まらないキーワード検索（段階的劣化） (Priority: P2)

埋め込み生成やバックフィルが未完了・失敗している状態でも、キーワード検索は従来どおり動作し続ける。ハイブリッド検索は、意味検索が利用できない範囲ではキーワード検索の結果にフォールバックする。

**Why this priority**: 可用性の保証。意味検索基盤の障害がシステム全体の検索停止につながらないことは、本番運用の前提。

**Independent Test**: 意味検索インデックスが空／一部欠損／生成失敗の各状態で、キーワード検索とハイブリッド検索を実行し、エラーで停止せず妥当な結果が返ることを検証できる。

**Acceptance Scenarios**:

1. **Given** 意味検索インデックスが空または欠損している, **When** キーワード検索を実行する, **Then** 従来どおり結果が返る。
2. **Given** 一部ドキュメントのみ意味検索対象化されている, **When** ハイブリッド検索を実行する, **Then** 意味検索対象外のドキュメントもキーワード一致で結果に含まれ、エラーにならない。
3. **Given** 埋め込み生成が失敗したドキュメントがある, **When** 任意の方式で検索する, **Then** そのドキュメントはキーワード検索では引き続き検索可能で、システム全体は劣化動作する（停止しない）。

---

### User Story 5 - 検索品質・データ整合性に関わる既存不具合の修正 (Priority: P1)

監査レポート（`specs/audit-report.md`）で Critical / High と判定された不具合のうち、検索品質とデータ整合性に直接関わるものを本機能の一部として修正する。これにより、ハイブリッド検索のスコア統合が信頼できる土台の上で行われる。

**Why this priority**: 既存のキーワード検索が体系的に取りこぼす・重複データが混入する状態のままでは、意味検索を足してもスコア統合が破綻する。ハイブリッド化の前提条件であり P1。

**対象とする監査項目（本機能スコープ内）**:
- A-1（Critical）: キーワード索引の言語構成と検索クエリの言語構成の不一致による検索取りこぼしの解消。索引化時とクエリ時で同一の言語構成を用いること。
- A-2（Critical）: 日本語ドキュメントが語単位で索引化されず検索に掛からない問題の解消。日本語クエリで日本語ドキュメントがヒットすること。
- A-3（High）: 同一内容ページの再クロールによる重複ドキュメント／重複断片の発生を、URL の一貫した正規化により防止すること。

**スコープ外（本機能では扱わない監査項目）**: 検索品質・データ整合性に直接関わらない項目（接続管理のリソースリーク E-1、並び順パラメータの未検証 D-3、出力フィールドのマッピング欠落 D-1 など）は別タスクとする。ただし重複の温床となる項目は A-3 に含めて扱う。

**Independent Test**: A-1 は語形変化する語（例: 複数形・活用）で取りこぼしが解消されることを、A-2 は日本語クエリで日本語ドキュメントがヒットすることを、A-3 は末尾スラッシュ／クエリパラメータ／リダイレクト差のある URL を再クロールしても重複行が増えないことを、それぞれ独立に検証できる。

**Acceptance Scenarios**:

1. **Given** 語形変化を含む英語ドキュメントがインデックスされている, **When** その語の別の語形で検索する, **Then** 索引とクエリの言語構成が一致しており該当ドキュメントが返る（A-1）。
2. **Given** 日本語ドキュメントがクロール済み, **When** 日本語の語句で検索する, **Then** 該当ドキュメントが返る（A-2）。
3. **Given** あるページが既にクロール済み, **When** 末尾スラッシュ・クエリ順・リダイレクトのみが異なる URL で再クロールする, **Then** 新規の重複ドキュメント・重複断片が作られない（A-3）。

---

### Edge Cases

- クエリが空文字、空白のみ、または極端に長い場合にどう振る舞うか（明確なエラーまたは空結果のいずれかで、無言クラッシュしない）。
- 検索対象データが 0 件のときに各方式が何を返すか（空結果＋件数 0、エラーにしない）。
- 意味検索のスコアとキーワード検索のスコアがスケールの異なる指標である場合に、統合ランキングがどちらか一方に偏らないこと。
- 同一ドキュメントがキーワードと意味の両方でヒットした場合に、結果が重複表示されず 1 件に統合され、両方式でヒットした旨が示されること。
- 日本語と英語が 1 つのドキュメント内に混在する場合に、両言語のクエリで適切に検索できること。
- バックフィル実行中に新規クロールが走った場合に、二重処理や取りこぼしが起きないこと。
- 再クロール時にコンテンツ変更が検知されたが意味表現の再生成に失敗した場合、古い意味表現を残すか破棄するか（古い表現を保持しつつ失敗フラグを立て、次回バックフィルで再試行対象にする）。
- 埋め込み生成が一部だけ失敗したドキュメントの扱い（完了した断片のみ意味検索対象とし、失敗断片は `failed` として対象外を明示する。FR-016 参照）。
- 結果件数の上限（limit）に 0・負数・上限超過が渡された場合の安全なクランプ。
- クロール・取得系ツールに内部・特権ネットワーク宛の URL（例: `http://169.254.169.254/...` クラウドメタデータ、`http://127.0.0.1:...` 内部サービス、`file:///etc/passwd` 等の非 HTTP スキーム）が渡された場合、取得せずに明確なエラーを返し、応答本文を結果に含めない（FR-020）。リダイレクト先・発見リンクが内部レンジへ向かう場合も同様に遮断する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、キーワード検索・意味検索・ハイブリッド検索の 3 方式を提供する検索ツールを公開しなければならない（MUST）。
- **FR-002**: 検索方式が指定されない場合、システムはハイブリッド方式を既定として使用しなければならない（MUST）。
- **FR-003**: ハイブリッド方式は、キーワード検索と意味検索の結果を RRF（Reciprocal Rank Fusion）で単一の統合ランキングに統合しなければならない（MUST）。RRF は両者の順位のみを用いるため、スコアのスケール差に関わらず中立な統合を保証する。
- **FR-004**: システムは、各検索結果に「どの方式でヒットしたか（キーワード／意味／両方）」と「数値スコア」を含めなければならない（MUST）。
- **FR-005**: 同一ドキュメント（または断片）が複数方式でヒットした場合、システムは結果を 1 件に統合し、両方式でヒットした旨を示さなければならない（MUST）。
- **FR-006**: 不正・未知の検索方式が指定された場合、システムは明確なエラーを返さなければならず、無言で既定方式に切り替えてはならない（MUST NOT）。
- **FR-007**: 新規にクロールされたドキュメントは、追加操作なしに自動的に意味検索の対象にならなければならない（MUST）。再クロールによりコンテンツの変更が検知された既存ドキュメントは、意味表現を自動的に再生成しなければならない（MUST）。コンテンツ未変更の場合は再生成しない。
- **FR-008**: システムは、既存のクロール済みドキュメントを意味検索対象に変換するバックフィル MCP ツールを提供しなければならない（MUST）。このツールは呼び出し時に即座に受付応答（処理開始の確認と対象件数の見込み）を返し、処理はバックグラウンドで継続される。
- **FR-009**: バックフィルの進捗（対象件数・完了件数・失敗件数・実行状態）は、別の MCP ツール（または `get_index_stats` の拡張）から確認できなければならない（MUST）。
- **FR-010**: バックフィルは再実行可能（冪等）でなければならず、既に処理済みのドキュメントを二重処理してはならない（MUST）。
- **FR-011**: 意味検索のためのデータ生成（埋め込み）が未完了・失敗している状態でも、キーワード検索は従来どおり動作し続けなければならない（MUST）。
- **FR-012**: ハイブリッド検索は、意味検索が利用できない範囲ではキーワード検索結果にフォールバックし、システム全体を停止させてはならない（MUST、段階的劣化）。
- **FR-013**: システムは、日本語と英語が混在する環境で、どちらの言語のクエリでも検索が機能しなければならない（MUST）。日本語ドキュメントは語単位で索引化され、日本語クエリで検索可能でなければならない（監査 A-2）。
- **FR-014**: キーワード検索の索引化時とクエリ時で同一の言語構成を用い、語形差による体系的な取りこぼしを起こしてはならない（MUST、監査 A-1）。
- **FR-015**: システムは URL を一貫して正規化し、末尾スラッシュ・クエリパラメータの並び・リダイレクト差のみが異なる URL の再クロールで重複ドキュメント／重複断片を生成してはならない（MUST、監査 A-3）。
- **FR-016**: 埋め込み生成が失敗した断片は、失敗として識別可能でなければならず、後続のバックフィル再実行で再試行の対象になり得なければならない（MUST）。埋め込み状態は断片（Content Chunk）単位で管理し、同一ドキュメント内で一部の断片のみ失敗した場合は、完了した断片のみを意味検索対象とし、失敗した断片は意味検索対象外（`failed`）として明示する（部分対象化）。
- **FR-017**: 検索ツールは、結果件数の上限（limit）に対し、0・負数・上限超過を安全な範囲にクランプしなければならない（MUST）。
- **FR-018**: 検索ツールは、サイト単位での絞り込みなど既存のキーワード検索が提供していた絞り込み・ページネーション機能を、全方式で維持しなければならない（MUST）。
- **FR-019**: 埋め込み生成のエンドポイント・モデル名・次元数は設定ファイルで指定可能でなければならない（MUST）。インターフェースは OpenAI 互換 API 形式とし、ローカル互換サーバと外部クラウド API の双方に対応する。システムはローカル／外部の区別を実装上意識せず、設定された接続先に対して同一のプロトコルで通信する。
- **FR-020**: クロール・ページ取得系ツール（`read_and_extract_page` / `crawl_component_docs` / `crawl_documentation_site`、およびリンク発見・robots/sitemap 取得を含む内部の URL 取得経路）は、外部から渡された URL を取得する前に SSRF 対策の検証を行わなければならない（MUST、セキュリティレビュー指摘）。具体的には次を満たすこと。
  - スキームは `http` / `https` のみを許可し、それ以外（`file:` / `gopher:` / `ftp:` 等）は明確なエラーで拒否する（MUST NOT 取得）。URL 正規化（FR-015）はスキーム・ホストを制限しないため、正規化とは別に検証を行う。
  - 名前解決後の接続先 IP がループバック（`127.0.0.0/8`, `::1`）・プライベート（RFC1918）・リンクローカル（`169.254.0.0/16`、クラウドメタデータ `169.254.169.254` を含む）・その他の内部レンジに該当する場合は取得を拒否する。DNS リバインディング対策として、検証時と接続時で同一の解決結果を用いる（接続時に再検証する）。
  - 検証は外部入力の URL（ツール引数）・クロール中に発見したリンク・sitemap/robots 由来の URL すべてに一貫して適用する。
  - 取得が拒否された場合は、その旨を呼び出し側へ明確なエラーとして返し、内部リソースの応答本文を結果に含めてはならない（MUST NOT）。

### Key Entities *(include if feature involves data)*

- **Document（ドキュメント）**: クロールされた 1 ページ分の内容。正規化された URL を一意キーとして持ち、重複を防ぐ。意味検索対象化の状態（未処理／完了／失敗）を持つ。
- **Content Chunk（断片）**: ドキュメントを検索・意味処理しやすい単位に分割したもの。キーワード索引と意味表現の両方の対象となる。
- **Semantic Representation（意味表現）**: 断片の意味的な内容を表す表現。生成のモデル世代を識別する情報と、生成日時を持つ。生成失敗を識別できる。
- **Search Result（検索結果）**: 検索で返る 1 項目。対象ドキュメント／断片への参照、ヒット方式（キーワード／意味／両方）、数値スコア、表示用の抜粋を持つ。
- **Backfill Job（バックフィル処理）**: 既存ドキュメントを意味検索対象化する処理単位。対象・完了・失敗の件数と進捗状態を持ち、冪等に再実行できる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 「概念は同じだが用語が異なる」評価用クエリ集合において、ハイブリッド検索（RRF 統合）の該当ドキュメント発見率（再現率）が、キーワード検索のみと比べて 30% 以上向上する。
- **SC-002**: 日本語クエリで日本語ドキュメントを検索した場合の該当ドキュメント発見率が、修正前の実質ゼロ近傍から 80% 以上に改善する（監査 A-2 の解消）。
- **SC-003**: 語形変化を含む英語クエリ評価セットで、修正前に取りこぼしていた該当ドキュメントの 95% 以上がハイブリッド／キーワード検索で返る（監査 A-1 の解消）。
- **SC-004**: 末尾スラッシュ・クエリ順・リダイレクト差のみが異なる URL を再クロールしても、重複ドキュメントが 0 件である（監査 A-3 の解消）。
- **SC-005**: 意味検索インデックスが空・一部欠損・生成失敗のいずれの状態でも、キーワード検索およびハイブリッド検索が停止せず結果を返す（段階的劣化の達成率 100%）。
- **SC-006**: すべての検索結果項目にヒット方式とスコアが付与されている（付与率 100%）。
- **SC-007**: バックフィルを 2 回連続実行した際、2 回目に再処理されるドキュメントが 0 件である（冪等性）。
- **SC-008**: 既定（方式無指定）の検索呼び出しの 100% がハイブリッド方式で実行される。
- **SC-009**: 応答時間目標は初期リリースでは設定しない。実装後に実測値を計測し、計測結果を基に本項目に数値目標を追記する。
- **SC-010**: クロール・取得系ツールに対し、ループバック・プライベート・リンクローカル（メタデータ含む）宛 URL および非 HTTP(S) スキームを与えたテストセットで、取得拒否率が 100% であり、内部リソースの応答本文が結果に一切含まれない（FR-020 の SSRF 対策の達成、セキュリティレビュー指摘の解消）。

## Assumptions

- 「監査レポートの Critical/High のうち検索品質・データ整合性に関わるもの」とは、`specs/audit-report.md` の A-1（FTS 言語不整合）・A-2（日本語未トークナイズ）・A-3（URL 正規化欠如による重複）を指すと解釈する。接続リーク（E-1）、並び順パラメータ未検証（D-3）、出力マッピング欠落（D-1）等は検索品質・データ整合性に直接関わらないため本機能スコープ外とし、別タスクで扱う。
- 意味検索の品質評価は、本機能の検証用に用意する評価クエリ集合（日本語・英語・言い換えを含む）に対して測定する。評価集合の整備は本機能の一部とする。
- 埋め込み生成のエンドポイント・モデル・次元は**設定ファイルで指定**する。インターフェースは OpenAI 互換 API 形式とし、ローカルで動く互換サーバ（例: Ollama）でも外部クラウド API でも、設定さえ合わせれば同等に動作する（ローカル／外部の区別をシステムは意識しない）。
- 既存の検索ツールが提供していたサイト単位の絞り込み・ページネーション・件数上限の仕様は、本機能でも維持される。
- バックフィルは既存ドキュメント量に対してバッチ的に実行でき、実行中も通常のクロール・検索が継続できることを前提とする。
- リランキング（cross-encoder 等）および検索 UI の提供は明示的にスコープ外。
- セキュリティレビュー（branch `001-hybrid-search`）で High と判定されたクロール・取得系ツールの SSRF（ホスト・プロトコルが外部入力で完全に制御可能）を、本機能のスコープに含める（FR-020 / SC-010）。本機能は新規ツールの追加と既存取得経路の改修を伴うため、新たに広がる取得面に対する SSRF 対策を本機能の一部として実装する。なお埋め込み生成の接続先は設定ファイル由来（信頼境界内）であり、本対策の対象は外部入力 URL を取得するクロール・ページ取得経路に限る。

## Clarifications

### Session 2026-06-13

- Q: 埋め込み生成の実行基盤（外部 API かローカルモデルか）→ A: OpenAI 互換 API 形式で統一し、エンドポイント・モデル・次元を設定ファイルで指定する。ローカル互換サーバと外部クラウド API を区別せず同一プロトコルで扱う。
- Q: ハイブリッド検索の応答時間目標 → A: 初期リリースでは数値目標を設定しない。実装後に実測値を基に SC-009 として追加する。
- Q: バックフィルの実行モデル → A: 非同期 MCP ツール。呼び出し時に即座に受付応答を返し、進捗・完了状況は別途確認できる。
- Q: 再クロール時の意味検索インデックス更新 → A: 自動更新。再クロールでコンテンツ変更が検知された場合、意味表現を自動的に再生成する。
- Q: スコア統合（ランキング融合）の方針 → A: RRF（Reciprocal Rank Fusion）を採用する。順位ベースの融合によりスコアのスケール差に頑健で、チューニングパラメータを最小化する。
