## Context

既存システムはNode.js/TypeScriptのstdio MCPサーバで、永続化にはPostgreSQLを使用している。全文検索は`tsvector`に依存していたが、索引時と検索時の言語構成が一致せず、日本語も適切に分割できなかった。一方、pgvector用テーブルは初期形だけ存在する。検索、クロール、DB、MCPツールを横断し、既存データの移行と外部URL取得のセキュリティを伴う変更である。

## Goals / Non-Goals

**Goals:**
- 日本語・英語キーワード検索と意味検索を単一の検索契約で提供する。
- スコア尺度に依存しない統合順位と、障害時の段階的劣化を実現する。
- 新規・更新データと既存データの埋め込みライフサイクルを運用可能にする。
- URL重複とSSRFを取得経路全体で防止する。
- 既存のサイト絞り込み、ページネーション、PostgreSQL資産を維持する。

**Non-Goals:**
- SQLite/FTS5への全面移行。
- cross-encoder等による再ランキング。
- 検索UIの提供。
- 初期リリースでの応答時間SLO策定。
- 監査レポート中、検索・URL取得に直接関係しない既存課題の修正。

## Decisions

### PostgreSQL内蔵のPGroongaとpgvectorを使用する

全文検索はPGroongaの単一索引へ移行し、ベクトルは別プロセスのベクトルDBではなくpgvectorへ保存する。既存のPostgreSQLトランザクション、外部キー、運用資産を維持でき、日本語トークナイズとベクトル近傍検索をDB内で完結できるためである。

代替案のSQLite/FTS5/sqlite-vecは、実コードと運用基盤の全面置換になるため採用しない。PostgreSQL標準`tsvector`の継続は日本語処理を満たさないため採用しない。

### 順位統合にRRFを使用する

キーワードスコアとコサイン類似度は尺度が異なるため、値を直接線形結合せず、各検索の順位から`Σ 1/(k+rank)`を計算する。同一チャンクIDを統合キーとし、両方に出た結果は`both`とする。

代替案の線形結合はモデルやコーパスごとの重み調整が必要で、初期導入の安定性を下げるため採用しない。

### 埋め込みはOpenAI互換APIへ統一する

ランタイム標準`fetch`で`/v1/embeddings`を呼び、接続先、キー、モデル、次元、バッチ、タイムアウトを設定化する。ローカル互換サーバとクラウドAPIを実装上区別せず、社内データを外部送信しない構成も選択可能にする。

ベクトル列の次元はDBスキーマで固定されるため、設定次元との整合性を起動・保存前に検証する。次元変更はスキーマ移行と再バックフィルを伴う。

### チャンク単位の状態とモデル世代を管理する

埋め込みはチャンクIDとモデル世代の組でupsertし、チャンクに状態、試行回数、エラー、モデル、更新時刻を持たせる。部分失敗時も成功チャンクを検索可能にし、更新失敗時は古いベクトルを保持する。

バックフィルは永続ジョブを作成して即時応答し、プロセス内ワーカーが小さなバッチで処理する。対象抽出は未処理・失敗だけとし、競合を避ける。実行中ジョブは1つに直列化する。

### 検索オーケストレータで縮退を制御する

`keyword`と`semantic`を独立モジュールにし、`hybrid`は両方を取得して融合する。意味検索の埋め込み生成、API、索引が失敗または空の場合、`hybrid`はキーワード結果を返し、`semantic`単独は空結果を返す。キーワード側の障害は隠蔽しない。

融合後にoffset/limitを適用するため、各検索から`limit + offset`件の候補をoffset 0で取得する。

### URL正規化とSSRF検証を分離する

正規化は重複防止だけを担当し、スキーム・接続先の許可判定はSSRFガードが担当する。URL入力、発見、robots、sitemap、リダイレクトの全取得前に名前解決済みIPを検証し、接続時IPとの一致も確認する。

## Risks / Trade-offs

- [PGroonga/pgvectorがホスト環境に未導入] → マイグレーションを明示的に失敗させ、Dockerの再現可能な検証環境とセットアップ手順を提供する。
- [埋め込みAPIの遅延・停止] → タイムアウト、失敗状態、再試行可能なバックフィル、キーワードへの縮退で影響を限定する。
- [バックフィルが通常処理とDB資源を競合] → 小バッチ、直列ジョブ、競合回避ロック、バッチ間待機を使用する。
- [固定ベクトル次元がモデル変更を制約] → モデル世代を記録し、次元変更時は明示的なDB移行と再生成を要求する。
- [RRFは元スコアの絶対的信頼度を捨てる] → 初期導入では尺度差への頑健性を優先し、再ランキングはスコープ外とする。
- [プロセス内バックフィルはプロセス再起動で中断] → 進捗をDBへ永続化し、再実行時に未完了・失敗だけを冪等に処理する。

## Migration Plan

1. PGroongaとpgvectorを対象PostgreSQLへ導入する。
2. PGroonga索引、チャンク埋め込み状態、HNSW索引、バックフィルジョブの順でマイグレーションを適用する。
3. 旧`tsvector`更新トリガーを停止し、既存`search_vector`を互換目的のnullable列として残す。
4. 埋め込み接続設定とDBベクトル次元の一致を確認する。
5. 新検索を有効化し、埋め込みがない間はキーワード縮退で運用する。
6. 既存チャンクのバックフィルを開始し、進捗と失敗数を監視する。
7. 日英検索、意味一致、縮退、URL重複、SSRF、カスケード削除を受け入れテストで確認する。

ロールバック時はMCPの検索既定をキーワードへ戻し、埋め込み生成とバックフィルを停止する。追加テーブルと索引は既存文書データから分離されているため、文書・チャンクを保持したまま無効化できる。
